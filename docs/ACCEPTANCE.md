# Malak v0.1 acceptance

This map groups the one-machine acceptance criteria and the tests that exercise them. Items are numbered within each table. **Partial** marks evidence for only part of a criterion. **Uncovered** marks a criterion without a test that directly exercises it. **Needs fixture** marks a criterion with available checks and a named external fixture for the remaining evidence. A protocol unit test is identified when the live path still needs a fixture.

The milestone 1 map has **97 Covered**, **7 Needs fixture**, **0 Partial** and **1 Uncovered**. The Uncovered item is import, which is outside milestone 1. The damage and recovery power-loss test is outside the milestone 1 completion gate. Its fixture is described below.

The real account tests use `MALAK_TEST_SECOND_ACCOUNT`. The third-account fixture also uses `MALAK_TEST_THIRD_ACCOUNT`. With those variables unset, the tests are explicitly ignored. Live tail carries owner outcomes, write and delivery metadata, and startup cut and damage reports. The private journal records the scope of each observed cut and distinguishes torn bytes from an authentic record with an abandoned stamp. General observer integration extends beyond the one-machine live tail.

Stock Markdown saves the filesystem ID and directory inode at first initialization. Without a host, apply requires matching saved identities and `--owner-vouches-same-volume` each time. The optional `board.store_place_socket` supplies host evidence and permits automatic continuation. The CLI tests exercise both paths.

### External fixtures

- **Power-loss filesystem.** A disposable virtual disk on a supported filesystem, with externally triggered virtual power cuts at writes, renames and syncs, followed by a fresh mount and ordinary restart or recovery. The process-kill tests exercise the same software boundaries while the kernel remains running.
- **Stateful protocol campaign.** A sustained coverage-guided run with a corpus of complete handshakes and participant and owner sessions, varied frame boundaries, reply placement, reordering, and injected deadlines. See [the bounded fuzz runs](../fuzz/README.md).
